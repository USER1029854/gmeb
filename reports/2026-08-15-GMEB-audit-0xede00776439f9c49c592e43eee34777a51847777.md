# Security Audit: utility/GMEB (FlapTaxTokenV3) — BSC

**Target:** `0xede00776439f9c49c592e43eee34777a51847777` (BSC, chainid 56)
**Scope of this document:** Exploitability assessment. Where the pre-audit mapping (`2026-08-15-GMEB-0xede0077…847777.md`) only resolved the dependency/authority graph and explicitly made **no** safety determination, this document performs the adversarial audit: it reasons from how the system moves value and grants authority, derives the invariants that must hold, and tries to break them from the position of a low-capital, unprivileged attacker.

**Method:** Full verified source for every value-custody / value-moving / authority contract was pulled from BscScan (Etherscan V2, `chainid=56`) and read end-to-end — the token, the Dividend contract, the TaxProcessor (`TaxProcessorUniV2` + `TaxProcessorBase` = `TaxProcessorCore`/`AdminImpl`/`DispatchImpl`), the quote token (`SecuritiesToken` + `ERC8056BaseUpgradeable`), its `Compliance`/`PauseManager`, the quote token's `ISSUER_ROLE`-holding wallets (`OperatorWallet`, `BurnWallet`), and `Portal`/`PortalBase`. Live config, wiring, role membership, and the access-control of the sensitive Portal paths were confirmed by `eth_call`/`eth_getStorageAt` and by **simulating the sensitive functions from both an unprivileged address and a privileged Safe** against BSC mainnet state.

**Snapshot:** 2026-08-15.

---

## Result: no qualifying unprivileged findings

After modelling the system, deriving invariants, and adversarially testing every value path and authority gate, **I found no economic exploit that passes the disproportionality gate, and no access/authority path an unprivileged attacker can reach.** Every fund-moving function is correctly guarded (verified in source and, for the Portal paths, live on-chain); the dividend/tax accounting is heavily and correctly hardened; and the one genuine code smell (a `minOutputAmount = 0` self-swap) is exploitable only through spot-price manipulation / sandwiching, which the scope excludes.

The real, material risk in this system is **centralization** — a small set of multisigs and single EOAs can move or redirect value. That is already documented in the mapping, and I re-confirmed the mechanics below. But it is a *trust assumption*, not an unprivileged-attacker-reachable exploit: every such path requires a privileged party to act. Per this audit's own gate ("attacker-reachable … not requiring a privileged party to misact"), those do not qualify as access findings. They are restated in **Assumptions & limitations** so the reader sees they were evaluated, not missed.

Reporting zero qualifying findings is, per the brief, a correct outcome here — this is a professionally-hardened codebase whose own comments cite the specific tests and failure modes they defend against, and my job was to verify those defenses actually hold (they do) rather than to manufacture findings.

## 1. System model — how GMEB moves value and grants authority

**What backs each unit of value.** GMEB is a fixed-supply (1e9 × 1e18, minted once, `owner()` renounced, **no `mint()`**) ERC-20 with an asymmetric transfer tax. The accounting identities that must hold:

- **Token supply is conserved** — only `_transfer` moves it; tax is just a redirect of part of a transfer to the token contract's own balance; there is no path that creates or destroys supply after `initialize()`.
- **Tax → quote → split.** Accrued tax (held at `address(this)`) is liquidated when a *sell* (`to == mainPool`) pushes the contract balance over `liquidationThreshold`. Liquidation hands the tax to `TaxProcessor.processTaxTokens`, which swaps tax→quote on the Pancake V2 pool and splits the quote into buckets by a fixed bps config. **Live config for GMEB:** `feeRate = 1000` (10%), `dividendBps = 10000` (100% of the post-fee remainder → 90% of tax), and `marketBps = deflationBps = lpBps = 0`. So the only active destinations are **fee → `feeReceiver` Safe** and **dividend → the Dividend contract**; buyback/burn, LP-add, and market-wallet paths are all **inert** for this token.
- **Dividend solvency.** `dividendToken == quoteToken == SecuritiesToken` (`0x46ceefda…`). Dividends are deposited (on the permissionless `dispatch()`) into a MasterChef-style `Dividend` contract and claimed by holders in proportion to `share` (= their live GMEB balance, floored at `minimumShareBalance = 10,000`). Invariant: the sum of all `withdrawable` never exceeds what was deposited.

**Where authority actually rests (confirmed live):**

| Gate on value | Guard | Who holds it |
|---|---|---|
| `TaxProcessor` sweep (`withdrawAll`) + all config setters | `onlyOwner` | Portal (`0xe2ce6ab8…`) |
| `Dividend` sweep (`emergencyWithdraw`) + `setDividendReceiver`/keepers/etc. | `onlyOwner` | Portal (same) |
| `TaxProcessor.processTaxTokens` | `onlyTaxToken` | the GMEB token only |
| `TaxProcessor.reconcileToken` | `require(msg.sender == address(this))` | self only |
| Portal → GMEB dividend/processor tweaks (`setTaxTokenDividendReceiver/Keeper`, `recoverStuckTaxProcessor`) | `DEFAULT_ADMIN_ROLE` / manage-role | Portal admin Safes |
| Portal proxy upgrade | ProxyAdmin → Safe 3-of-4 | `0x1f96bc88…` |
| Quote token mint/burn/UI-multiplier | `DEFAULT_ADMIN_ROLE` / `ISSUER_ROLE` | EOA `0x45e35fe9…` + issuer wallets (owner/operator EOAs `0xa42436…`, `0xb2f56f…`) |
| Quote token beacon upgrade | `beacon.owner()` | single EOA `0x4333daf4…` |

Every one of these is a *privileged* gate. The audit question is whether any of them is missing, bypassable, or reachable without the privileged key — and whether any *permissionless* path lets value flow to an attacker.

---

## 2. Invariants targeted

1. **Supply conservation** — no post-init mint/burn of GMEB reachable by anyone.
2. **Tax custody** — accrued tax at `address(this)` is only removable by the token's own liquidation into the fixed `taxProcessor`; no external actor can pull it.
3. **Bucket solvency** — `feeQuoteBalance + marketQuoteBalance + pendingDividendQuoteTokenBalance + lpQuoteBalance + preBondBurnFunds + commissionQuoteBalance ≤` the processor's actual quote balance, and buckets only pay owner-configured receivers.
4. **Dividend solvency** — Σ `withdrawableDividendOf` ≤ `totalDividendsDistributed − Σ withdrawn`; no double-claim; `share == 0 ⇒ rewardDebt == 0`.
5. **No share inflation** — a holder's `share` never exceeds their live balance; nobody can raise their share or lower another's except through real balance changes.
6. **Access integrity** — every fund-mover / redirect / role-grant checks an authority the attacker cannot obtain; no fund-mover reachable by an arbitrary caller.
7. **No leaked credential** — no key/signer/secret that gates value is hardcoded, derivable, or sitting in deployed bytecode.
8. **Quote-token accounting is standard** — the ERC-8056 UI multiplier must not change real balances (else pool/dividend accounting breaks).
9. **Reentrancy safety** — the transfer → liquidation → swap → `_afterTokenTransfer` → `setShare` call graph cannot be re-entered to double-count or desync state.
10. **Initialization integrity** — no live clone/proxy is un-initialized or re-initializable.

## 3. Findings

**None that qualify.** The candidate that came closest (dividend-deposit timing) fails the disproportionality gate by 35–50×; the one code smell (self-swap with no min-out) is out of scope as spot-manipulation/MEV. Both are documented in Coverage with the arithmetic / reasoning that killed them.

## 4. Coverage — candidates considered and dismissed

Each line is a candidate I actually chased down, with the concrete reason it does not survive.

**Economic**

- **Dividend-deposit timing (buy share → force `dispatch()` deposit → claim → sell).** *Dismissed — fails disproportionality, decisively.* `share` is capped at the holder's live balance, and the pool holds only ~29M GMEB / ~5,829 quote against `totalShares ≈ 961.3M`. To capture fraction `f` of a pending dividend pool `P`, the attacker must buy `f×961.3M` GMEB; break-even needs `P` ≈ 200k quote at `f=0.001` and ≈ 289k quote at `f=0.01` — 35–50× the *entire* pool's quote reserve — and `f≥0.05` is unbuyable (exceeds pool GMEB). Gain scales with the (pool-depth-capped) stake and requires other traders to have pre-funded `P`. Not disproportionate; not stake-independent.
- **`_swapTokensForQuote` / buyback with `amountOutMin = 0` (no slippage bound).** *Dismissed — out of scope.* This is the only `minOut=0` swap active for GMEB (deflation/LP/buyback buckets are 0, so the buyback path is inert). Without price distortion the swap executes at the true pool price (only normal ~<1% AMM slippage on a ~one-gap sell); value is lost **only** if the attacker distorts the spot price (flash-loan crash + rebuy) or sandwiches the forced swap — exactly the excluded "spot-price manipulation / front-running / MEV" class. There is no protocol-internal mispricing driving it (the swap reads the live pool, not a stale/internal number), so the "code-rooted mispriced redemption" carve-in does not apply. Noted as a defense-in-depth gap in §5.
- **Permissionless `dispatch()` misuse.** *Dismissed — no attacker payout.* Buckets are cleared checks-effects-interactions and paid only to owner-configured receivers (fee Safe, Dividend contract); `nonReentrant`; for GMEB market/commission are 0. Calling it early just distributes protocol funds to their intended destinations.
- **Permissionless `processBondingCurveTax(amount)` / `deposit(amount)` / reconcile-surplus.** *Dismissed — donations.* Each pulls the funds *from the caller* (`safeTransferFrom(msg.sender, …)`) and books them into protocol buckets / the dividend accumulator; there is no path back to the caller. Griefing-by-donation at worst.
- **mdps / `setShare` overflow → bricked transfers (self-inflicted DoS as griefing).** *Dismissed — unreachable.* GMEB supply 1e27 < 2¹²⁸, so `fullMulDiv(share, mdps, 2¹²⁸)` cannot overflow for any balance; driving `magnifiedDividendPerShare` to 2²⁵⁶ needs ~1e60 wei of dividends at the share floor. Attacker cannot approach either bound. `deposit()` reverts (never corrupts) on a pathological amount.
- **Share-dilution / "buy before dividend."** *Dismissed — intended mechanic, proportional to stake.* Joining before a deposit dilutes the joiner too (mdps divided by `totalShares` *including* their new share) and costs 1% tax + price impact; it is ordinary dividend-join timing, not extraction.
- **Deferral-window forfeiture (`deferredOrigins`).** *Dismissed — bounded, self-inflicted, owner-set.* Deferral only skips a *first-receive* write (`currentShare==0 && share>0`), never a decrease (the load-bearing rule that blocks the "sell-but-keep-share" flash-loan drain the code comments describe); it is keyed on owner-set origins, and being deferred *forfeits* dividends (hurts the deferred party). Not attacker-installable, not attacker-beneficial.

**Access / authority**

- **`TaxProcessor.withdrawAll` / `Dividend.emergencyWithdraw` / `setDividendReceiver`.** *Dismissed — `onlyOwner` (Portal); attacker cannot reach.* The `withdrawAll` delegatecall to `ADMIN_IMPL` preserves `msg.sender` and reads the clone's owner, so the guard is genuine; direct calls to the impl revert (`_disableInitializers` ⇒ owner 0).
- **Portal reaching into GMEB (`setTaxTokenDividendReceiver/Keeper`, `recoverStuckTaxProcessor`).** *Dismissed — access-controlled, confirmed live.* Simulated from an unprivileged address: `setTaxTokenDividendReceiver`/`…Keeper` revert with custom auth error `0x50f69a4e`; `recoverStuckTaxProcessor` reverts `AccessControl … missing role 0x00…0` (DEFAULT_ADMIN). Simulated from the DEFAULT_ADMIN Safe (`0x1f96bc88…` / `0x8a08d98c…`): all **succeed** — proving `0x50f69a4e` is the authorization gate, not a universal revert.
- **Quote-token (`SecuritiesToken`) mint to drain the pool.** *Dismissed — issuer path is EOA-gated.* `mint()` requires `DEFAULT_ADMIN_ROLE`/`ISSUER_ROLE`. The two contract issuers are `OperatorWallet` and `BurnWallet` (transparent proxies, same ProxyAdmin); `OperatorWallet.mint` is `onlyOperatorAndOwner` and `BurnWallet.burn` is `onlyOwner`, with owner/operator being EOAs (`0xb2f56f…`, `0xa42436…`). No permissionless mint-forward exists. Centralized, not attacker-reachable.
- **ERC-8056 UI-multiplier "rebase" to desync pool/dividend accounting.** *Dismissed — display-only + admin-gated.* The multiplier only affects `toUIAmount`/`balanceOfUI`/the `TransferWithUIAmount` event; real ERC-20 `balanceOf`/`_update` use raw amounts, so pool reserves and dividend shares are untouched. `setUIMultiplier` is `_authorizeMultiplierUpdate ⇒ admin/issuer` and bounded to [1e9, 1e27].
- **`Compliance` / `PauseManager` permissionless freeze/pause (DoS on the pool asset).** *Dismissed — fully role-gated* (`onlyBlocklistRole` / `onlyPauseRole`); no permissionless entry.
- **Reentrancy in transfer → `_liquidateTax` → `processTaxTokens` → swap → `_afterTokenTransfer`.** *Dismissed — guarded.* `poolState.notLiquidating` is set false (and persisted) before the external call, so nested `_liquidateTax` is skipped and nested transfers read `tax = 0`; the processor's `_swapping` flag parks nested `processTaxTokens`; the only external callees are the trusted processor and Pancake pair (empty-data swap, no attacker callback). No attacker injection point exists in this synchronous, protocol-internal graph.
- **Uninitialized / re-initializable clones or proxies.** *Dismissed — none.* Token, processor, dividend clones and the SecuritiesToken/Portal proxies are all live and initialized (`owner()`/roles set), and every implementation calls `_disableInitializers()` in its constructor.
- **Hardcoded/derivable credential gating value.** *Dismissed — none found.* No embedded signer/secret; EIP-2612 `permit` is signed by the token holder; `tx.origin` in `Dividend` is used only as an EOA *identifier* for the deferral optimization, never as an authorization check.
- **Alternative-pool tax avoidance (a pool not in the `pools` map is untaxed).** *Dismissed — not value extraction.* Trading GMEB on a pool the deployer didn't register merely avoids the tax; it robs no honest holder and creates no protocol shortfall.
- **`SwapRegistry` (unverified impl behind a single-EOA proxy).** *Dismissed for GMEB — inert.* Reachable only via the custom-dividend-token conversion branch, which requires `dividendToken ∉ {quoteToken, taxToken}` and a set `converter`; GMEB has `dividendToken == quoteToken` and `converter == 0`, so the registry is never called. It would only activate if Portal (owner) repointed the dividend token — a privileged action.

## 5. Assumptions & limitations

- **Centralization is the dominant real risk, and it is out of this audit's *attacker-reachable* class, not out of mind.** A compromise or malicious action of any of: the two Portal admin Safes (which own the processor + dividend and can `withdrawAll`/`emergencyWithdraw`/`setDividendReceiver`), the SecuritiesToken `DEFAULT_ADMIN` EOA or issuer-wallet EOAs (mint the pool's quote asset), or the SecuritiesToken **beacon-owner EOA** `0x4333daf4…` (rewrites the quote-token logic behind the pool and dividends) — would let that privileged party drain or redirect GMEB-related value. These are single points of trust (two of the four "keys" are lone EOAs, and the beacon EOA's blast radius spans sibling tokens too). They require the privileged actor to act, so they are trust assumptions rather than unprivileged exploits, but they are the thing most worth hardening (timelock/multisig the EOAs; the mapping §3 lists them).
- **`minOutputAmount = 0` on the tax-liquidation self-swap** is a legitimate defense-in-depth weakness that a general audit would flag (tax revenue is exposed to sandbagging/sandwich value loss). This audit's scope excludes the realization mechanism (spot manipulation / MEV), so it is not reported as a finding — but if the scope were broader, adding a sane `amountOutMin` (or routing through the same MEV-protected converter the platform already has) is the fix.
- **`SwapRegistry` implementation (`0x9a681bc1…`) is unverified bytecode** — I could not read it. It is inert for GMEB today (see Coverage), so it does not affect the current conclusion; if Portal ever repoints GMEB's dividend token to a custom token, this contract enters the value path and would need its own review.
- **Portal's satellite modules** (`PORTAL_TRADE_V2`, `PORTAL_TWEAK`, `PORTAL_ROLLER`, `PORTAL_LAUNCHER`, `PORTAL_LENS` — separate delegatecall targets) were not read line-by-line; I confirmed the specific tweak entrypoints that touch GMEB's contracts are access-controlled by live simulation, and for a DEX-graduated token the trade/curve/launcher modules are off GMEB's honest-user value path (users trade the Pancake pool directly; the processor's only Portal swap, the buyback, is inert at `deflationBps = 0`). A permissionless value-extracting bug inside an unread module remains a residual, un-eliminated possibility.
- **Off-chain / historical facts** (deployer identity, full holder distribution, the `metaURI` contents, and full membership of Portal's non-admin roles and the shared beacon) were not obtainable on the available RPC/API tier — same limits noted in the mapping. None of them change the on-chain reachability conclusions above.

---

## 6. Calibration

- **Severity/impact of what exists:** the highest-impact issues (fund sweep, dividend redirect, quote-asset mint, beacon logic swap) are all real but **privileged** — severity is bounded by the trust placed in the key-holders, not by a reachable code flaw. No unprivileged path to protocol funds was found, so there is no high-severity access finding to raise.
- **Confidence:** high that the *core* value/authority paths (token, dividend, tax processor, quote token, and the Portal entrypoints touching them) are not unprivileged-exploitable — this rests on complete source reads plus live simulation of the sensitive gates, not on trusting the code's own comments. Confidence is *moderate* only where it must be: the unverified `SwapRegistry` and the unread Portal satellite modules, both of which are off GMEB's current active path.
- **Economic gate:** the one economic candidate was dismissed with explicit arithmetic showing the break-even is 35–50× the pool's own liquidity — not a marginal call.

*Prepared as the exploitability pass complementing the pre-audit mapping. No safety guarantee is implied for the privileged/centralization surface, which is a governance/key-management concern rather than an unprivileged-attacker finding.*
